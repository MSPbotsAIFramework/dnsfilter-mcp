## Requirement understanding

One line: Review org/network/policy configuration, content categories, and traffic/threat reporting via DNSFilter.

The requester wants the Agent platform to have read-only visibility into a customer's DNSFilter
deployment: which organizations/networks exist, what filtering policy is applied to each network
(block/allow lists, blocked content categories, safe-search enforcement), what the DNSFilter content
category taxonomy looks like, and traffic/threat reporting (request volume, blocked/threat counts,
top categories/domains) over a time window. The goal is for an agent to answer "what is this
customer's DNS filtering policy" or "what threats did DNSFilter see on this network recently"
without a human logging into the DNSFilter dashboard. Nothing in the ticket text asks for the
ability to change a customer's live filtering policy from an agent.

## Product design

### Goals / Non-goals

Goals (v1):
- Read access to a DNSFilter account's organizations and networks, including which policy applies
  to which network.
- Read access to a network/policy's filtering configuration: allow/block domain lists, blocked
  content categories, per-search-engine safe-search enforcement, YouTube restriction, allow-list-only
  mode.
- Read access to the DNSFilter content category taxonomy (so category ids returned by the policy and
  report tools can be resolved to human-readable names).
- Read access to traffic and threat reporting: aggregate request/threat counts over a time window,
  and "top N" breakdowns (by category, domain, network, organization) needed to answer "what
  happened" questions.
- First version is read-only end to end.

Non-goals (v1):
- Writing or editing policies, networks, organizations, or block pages. DNSFilter policies gate what
  an end-user's network can reach; an agent silently toggling a block/allow list is a
  customer-impacting action the ticket's wording ("Review ...") does not ask for. If write access is
  wanted later it is new scope — it needs its own confirm/guardrail story (destructive-tool handling
  per the MCP SOP), not a default-on tool bundled into this read-only ticket.
- Billing/invoices, MSP/distributor management, end-user/agent (DNSFilter roaming-client) device
  management, PSA integration links, scheduled reports, API-key management. The ticket's own wording
  scopes to "org/network/policy configuration, content categories, and traffic/threat reporting";
  DNSFilter's full API surface (229 endpoints) is far broader than that.
- Bulk/raw query-log export. DNSFilter's own docs state the `query_logs` endpoint "is intended for
  investigation and reporting. It is not designed for bulk or continuous log export" (paginated at
  1,000 rows); the ticket does not name a log-export capability, and the top-N / summary reports
  (AC5, AC6) already cover the "traffic/threat reporting" ask without needing raw logs.
- Any change to the MCP gateway or control plane — nothing in this ticket needs one.

### Acceptance criteria

- AC1: Given the gateway passes a valid DNSFilter API key in the `X-Dnsfilter-Api-Key` header, when
  an agent calls `dnsfilter_list_organizations`, then it returns the organizations visible to that
  key (id, name, type), paginated.
- AC2: Given a valid API key, when an agent calls `dnsfilter_get_organization` with an organization
  id, then it returns that organization's basic information (name, address, feature flags), or a
  `not_found` error if the id is not visible to the key.
- AC3: Given a valid API key, when an agent calls `dnsfilter_list_networks` (optionally filtered to
  an organization), then it returns networks (id, name, protected/unprotected, which organization and
  which policy id each belongs to), with any live network secret key redacted from the response.
- AC4: Given a valid API key and a policy id, when an agent calls `dnsfilter_get_policy`, then it
  returns that policy's full configuration: allow/block domain lists, blocked category ids, per-engine
  safe-search flags, YouTube restriction, allow-list-only flag, and which networks/organization it
  applies to.
- AC5: Given a valid API key, when an agent calls `dnsfilter_list_policies` (optionally filtered to an
  organization), then it returns the policies defined for that scope (id, name, organization id,
  whether it is a global policy).
- AC6: Given a valid API key, when an agent calls `dnsfilter_list_categories`, then it returns the
  DNSFilter content category taxonomy (id, name, description, whether it is security-flagged), so
  category ids from AC4/AC8 can be resolved to names.
- AC7: Given a valid API key and a time range, when an agent calls `dnsfilter_get_traffic_summary`
  with `metric="requests"` or `metric="threats"`, then it returns the aggregate count for that metric
  over the window (optionally scoped to an organization or network, and bucketed over time when a
  `bucket_size` is given).
- AC8: Given a valid API key and a time range, when an agent calls `dnsfilter_get_top_report` with a
  `dimension` of `categories`, `domains`, `networks`, or `organizations`, then it returns the top-N
  entries for that dimension's threat/blocked activity in the window.
- AC9: Given the `X-Dnsfilter-Api-Key` header is missing or empty, when any tool is called, then the
  service returns a structured `unauthorized` error without calling DNSFilter.
- AC10: Given DNSFilter responds with 429, when any tool is called, then the service retries with
  backoff honoring `Retry-After`, and if still rate-limited after retrying, returns a structured
  `rate_limited` error (never a raw exception or an unhandled 5xx).
- AC11: Given an organization/network/policy id that does not exist or is not visible to the supplied
  API key, when a `get_*` tool is called, then it returns a structured `not_found` error, not an
  empty 200 or a 500.
- AC12: Given a `list_*` tool is called and the underlying DNSFilter query matches nothing, then the
  tool returns an empty collection (`"items": []`), not a `not_found` error.
- AC13: Given two concurrent tool calls carrying different `X-Dnsfilter-Api-Key` values (two different
  MSPbots tenants/customers calling through the same running container), when both are in flight at
  once, then neither call's outbound request to DNSFilter ever carries the other call's API key
  (request-level credential isolation; this is the multi-tenant boundary for a stateless connector
  that has no platform tenant field of its own — see Tech design §7).

Open questions:
- [已假设] DNSFilter's `Authorization` header takes the raw API key value with no scheme prefix (per
  `https://api.dnsfilter.com/docs`: "Authentication is required for most, but not all, endpoints, and
  is done by setting the Authorization request header, with the header value being the API key
  itself" — confirmed by the docs' own curl example, `curl -H 'Authorization: ***' .../v1/users/self`).
  Assumed correct; if wrong, only `client.py`'s outbound-call helper changes (Tech design §4), no tool
  contract changes.
- [不阻塞] Whether to also expose DNSFilter's raw `query_logs` endpoint as an additional tool, beyond
  the aggregate/top-N reports in AC7/AC8. Not named in the ticket; left out of v1 (see Non-goals) and
  recorded under `Decisions made by DEV01` (Tech design). Can be added later as a purely additive tool
  without touching any existing tool's contract.

## Tech design

### Conclusion

Build `dnsfilter-mcp` from scratch as a stateless Streamable-HTTP MCP server (Python 3.12 + uv +
FastMCP), matching the shape of the existing `cisco-umbrella-mcp` / `sonicwall-mcp` connectors in
MSPbotsAIFramework: one `httpx`-based client class wrapping DNSFilter's public REST API
(`https://api.dnsfilter.com`), credentials read per-request from an `X-Dnsfilter-Api-Key` header
(DNSFilter itself is a simple static-API-key vendor — no OAuth, no DB, no background jobs). Nine
read-only tools map onto DNSFilter's `/v1/organizations`, `/v1/networks`, `/v1/policies`,
`/v1/categories`, and `/v1/traffic_reports/*` endpoint groups (229 endpoints total in the vendor's
API; nine tools is a deliberate consolidation per SOP A4 "tools are capabilities, not endpoint
mirrors").

- `pyproject.toml` — Python 3.12; deps `fastmcp`, `httpx`, `pydantic`, `pydantic-settings`; dev deps
  `pytest`, `pytest-asyncio`, `respx` (HTTP mocking, so tests never call the real DNSFilter API).
- `src/dnsfilter_mcp/server.py` — FastMCP app factory, `stateless_http=True`, mounts `POST /mcp` +
  `GET /health`; `TransportSecuritySettings(enable_dns_rebinding_protection=False)`; lifespan mounted
  on the outer app (SOP §7, not the mounted sub-app) so `/mcp` doesn't 500 with "Task group is not
  initialized" while `/health` stays 200.
- `src/dnsfilter_mcp/settings.py` — `pydantic-settings`, `SettingsConfigDict(extra="ignore")`;
  `MCP_HTTP_HOST` / `MCP_HTTP_PORT`, default `0.0.0.0:8080`.
- `src/dnsfilter_mcp/auth.py` — middleware reads `X-Dnsfilter-Api-Key` from the incoming MCP request,
  `set`/`reset` via a `contextvars.ContextVar` (request-scoped, never a module-level/global); missing
  or empty header → 401 body listing the required header (covers AC9).
- `src/dnsfilter_mcp/client.py` — `httpx.AsyncClient` against `https://api.dnsfilter.com`; sets
  `Authorization: <api key>` (raw value, from the context var, see Open questions) on every outbound
  call; connect/read timeouts 5s/30s; retries 429/5xx with backoff honoring `Retry-After`; one logical
  tool call's total outbound time budget < 120s; one `AsyncClient` instance reused across requests
  within a worker (connection pooling), never caching response bodies across requests.
- `src/dnsfilter_mcp/errors.py` — maps DNSFilter HTTP responses to the SOP error envelope
  `{"error":{"code","message","retryable"}}`: 401/403 → `unauthorized` (`retryable=false`), 404 →
  `not_found` (`retryable=false`), 400/422 → `invalid_argument` (`retryable=false`), 429 →
  `rate_limited` (`retryable=true`), 5xx/timeout/connection error → `upstream_error`
  (`retryable=true`). DNSFilter's own error body is `{"error": "<message>"}` (confirmed from the
  OpenAPI `Error` schema); that string is passed through as `message`.
- `src/dnsfilter_mcp/pagination.py` — shared helper: DNSFilter's list responses carry a JSON:API
  `links.self` with no `has_more`/`total` field, so `has_more` is derived (`true` when the page
  returned exactly the requested `page[size]`, `false` otherwise) and documented as a heuristic in
  each list tool's description.
- `src/dnsfilter_mcp/tools/organizations.py` — `dnsfilter_list_organizations` (`GET
  /v1/organizations`), `dnsfilter_get_organization` (`GET /v1/organizations/{id}`).
- `src/dnsfilter_mcp/tools/networks.py` — `dnsfilter_list_networks` (`GET /v1/networks`; filters
  client-side by `relationships.organization.data.id` when `organization_id` is given, since

- `src/dnsfilter_mcp/tools/policies.py` — `dnsfilter_list_policies` (`GET /v1/policies`, native

- `src/dnsfilter_mcp/tools/categories.py` — `dnsfilter_list_categories` (`GET /v1/categories`).
- `src/dnsfilter_mcp/tools/reports.py` — `dnsfilter_get_traffic_summary` (wraps `GET

### Data & API contract

All tools return a single JSON string (SOP §4: a compact-serialized, `ensure_ascii=False`, no
`indent=2`). Vendor endpoint cited as `METHOD path` from `dnsfilter-openapi@2026-10-27`
(`https://api.dnsfilter.com/docs/api.json`).

**`dnsfilter_list_organizations`** — `GET /v1/organizations`
- Args: `name?` (string, substring filter), `type?` (`normal|msp|sub_organization`), `limit?`
  (default 25, max 100 → DNSFilter `page[size]`), `page?` (default 1 → DNSFilter `page[number]`).
- Returns: `{"items":[{"id","name","type","allow_create_network"}...],"has_more":bool}`.
- Errors: `unauthorized`, `rate_limited`, `upstream_error`.

**`dnsfilter_get_organization`** — `GET /v1/organizations/{id}`
- Args: `organization_id` (required, integer).
- Returns: `{"id","name","address","feature_flags","canceled"}`.
- Errors: `unauthorized`, `not_found` (DNSFilter 404 or id not visible to this key), `rate_limited`,
  `upstream_error`.

**`dnsfilter_list_networks`** — `GET /v1/networks` (+ client-side filter on
`relationships.organization.data.id`)
- Args: `organization_id?` (integer), `search?` (string), `protected?` (bool), `limit?` (default 25,
  max 100), `page?` (default 1).
- Returns: `{"items":[{"id","name","organization_id","policy_id","protected"}...],"has_more":bool}`
  — `secret_key` is never included.
- Errors: `unauthorized`, `rate_limited`, `upstream_error`.

**`dnsfilter_get_network`** — `GET /v1/networks/{id}`
- Args: `network_id` (required, integer).
- Returns: `{"id","name","organization_id","policy_id","protected","local_domains"}` —
  `secret_key` omitted.
- Errors: `unauthorized`, `not_found`, `rate_limited`, `upstream_error`.

**`dnsfilter_list_policies`** — `GET /v1/policies`
- Args: `organization_id?` (integer), `include_global_policies?` (bool, default true), `limit?`
  (default 25, max 100), `page?` (default 1).
- Returns: `{"items":[{"id","name","organization_id","is_global_policy"}...],"has_more":bool}`.
- Errors: `unauthorized`, `rate_limited`, `upstream_error`.

**`dnsfilter_get_policy`** — `GET /v1/policies/{id}`
- Args: `policy_id` (required, integer).
- Returns: `{"id","name","organization_id","whitelist_domains","blacklist_domains",
  "blacklist_categories","allow_list_only","allow_unknown_domains","google_safesearch",
  "bing_safe_search","duck_duck_go_safe_search","ecosia_safesearch","yandex_safe_search",
  "youtube_restricted","youtube_restricted_level","network_ids"}` (network_ids flattened from
  `relationships.networks.data[].id`).
- Errors: `unauthorized`, `not_found`, `rate_limited`, `upstream_error`.

**`dnsfilter_list_categories`** — `GET /v1/categories`
- Args: `limit?` (default 50, max 100), `page?` (default 1).
- Returns: `{"items":[{"id","name","description","security","internal"}...],"has_more":bool}`.
- Errors: `unauthorized`, `rate_limited`, `upstream_error`.

**`dnsfilter_get_traffic_summary`** — `GET /v1/traffic_reports/total_requests` |
`GET /v1/traffic_reports/total_threats`
- Args: `metric` (required, `requests|threats`), `from` (required, ISO 8601), `to` (required, ISO
  8601), `organization_id?`, `network_id?`, `bucket_size?` (string, e.g. `day`; passed through to
  DNSFilter), `type?` (`all|allowed|blocked`, default `all`).
- Returns: `{"metric","from","to","buckets":[{"timestamp","count"}...],"total":int}`.
- Errors: `unauthorized`, `invalid_argument` (bad `from`/`to`/`metric`), `rate_limited`,
  `upstream_error`.

**`dnsfilter_get_top_report`** — `GET /v1/traffic_reports/top_categories` |
`.../top_domains` | `.../top_networks` | `.../top_organizations_requests`
- Args: `dimension` (required, `categories|domains|networks|organizations`), `from` (required), `to`
  (required), `organization_id?`, `network_id?`, `security_report?` (`all|true|false`, default
  `true` — scopes to threat/security-flagged activity, matching the ticket's "threat reporting" ask),
  `limit?` (default 10, max 50).
- Returns: `{"dimension","from","to","items":[{"key","label","count"}...]}` (`key`/`label` shaped per
  dimension — e.g. `{"key":"142","label":"Malware"}` for categories, `{"key":"evil.example.com",
  "label":"evil.example.com"}` for domains).
- Errors: `unauthorized`, `invalid_argument`, `rate_limited`, `upstream_error`.

No DB, no migrations — this service is stateless and holds no data of its own. No breaking change to
anything (new repo, nothing to be backward-compatible with yet).

### Key flow / sequence

```
Agent → Gateway (adds X-Dnsfilter-Api-Key from the stored credential)
      → POST /mcp (dnsfilter-mcp) → auth middleware: ContextVar.set(api_key)
      → tool fn → client.py: httpx GET https://api.dnsfilter.com/v1/<resource>
                              Authorization: <api_key>
      ← DNSFilter response (200 | 4xx | 429 | 5xx)
      → errors.py maps non-2xx → {"error":{code,message,retryable}}
      ← tool returns compact JSON string
      → auth middleware: ContextVar.reset() (finally block, always runs)
```

### Non-functional

- **Idempotency & concurrency**: every tool is a GET against DNSFilter; no local state to race on.
  Two concurrent calls on the same container never share the `httpx.AsyncClient`'s per-call auth
  header because the header is read from the request-scoped `ContextVar`, not a shared client
  default (AC13).
- **Performance**: list endpoints default to 25–50 items, hard-capped at 100 (DNSFilter's own max);
  `dnsfilter_get_top_report` caps at 50. Outbound timeout 5s connect / 30s read; total tool-call
  budget < 120s including retries.
- **Security**: credential only ever read from `X-Dnsfilter-Api-Key`, never logged, never written to
  disk, never falls back to an environment variable (SOP §3.1's "never read Header-or-env" rule).
  **`secret_key`** (DNSFilter's own field on a `Network` object — a live credential used by that
  network's user-agents/LAN proxies to authenticate to DNSFilter, confirmed present in the `Network`
  schema of the vendor's own OpenAPI spec) is stripped from every response this service returns;
  returning it to an agent/LLM context would hand out a working DNSFilter credential as "just data".
  This is the one field-level redaction this design makes; no other field in scope is sensitive in
  the same way.
- **Multi-tenant isolation**: this connector has no concept of an MSPbots tenant of its own — isolation
  is enforced by the gateway supplying a different `X-Dnsfilter-Api-Key` per MSPbots customer and this
  service never caching or sharing that key across requests (AC13, enforced by `contextvars` +
  `tests/test_middleware.py`).
- **Observability**: structured log line per tool call (tool name, DNSFilter endpoint, status code,
  latency, retry count) with the API key value never logged (log the header name's presence, not its
  value).

### Rollout & rollback

Brand-new connector; nothing to migrate and nothing currently depends on it. Rollout is "register with
the MCP gateway and deploy to INT" (`/api/vendor-register`, since this is the first version of a new
vendor — see mcp-track.md §4.8). Rollback is simply not registering/using the connector; no customer
is configured to use it yet, so there is no in-flight traffic to drain.

  the data returned matches what a human sees in the DNSFilter dashboard for the same org/network/
  policy (see `.ac.json` TC-DNSF-012) — this does not block merging, developing, or publishing to INT
  per the SOP's "no test account is not a blocker" rule; it is recorded for whenever a real account
  becomes available.
- Regression surface: none — new repo, no existing behavior to regress.

### Effort & breakdown

Rough order of magnitude: **2–4 person-days** for a single engineer, SOP skeleton + 9 read-only tools
+ tests + Docker + README. Main source of uncertainty: exact JSON:API nesting DNSFilter actually
returns in practice for list endpoints with the `page[...]` object-shaped query param (this design
read the OpenAPI spec but has not yet made a live call) — if the pagination query param needs a
different serialization (e.g. `page[number]=1&page[size]=25` vs. a JSON-encoded `page` value), that's
a `client.py`-local fix, not a tool-contract change.

Suggested sub-tasks (each independently demoable): (1) skeleton + auth middleware + health check; (2)
organizations + networks + policies + categories tools; (3) traffic/threat report tools; (4)
tests/Docker/README + SOP §14 checklist pass.

### Risks & dependencies

- **Risk**: DNSFilter's `page[...]` query parameter is documented as an object
  (`{"number":int,"size":int}`), which most HTTP clients don't serialize to query string
  automatically — `client.py` needs to build it explicitly as `page[number]=N&page[size]=M`.
  Mitigation: covered by the unit tests against `respx`-mocked requests that assert the exact query
  string sent.
- **Risk**: the Open question's assumption about the bare-value `Authorization` header (no scheme
  prefix) turns out to be wrong in practice. Mitigation: isolated to one line in `client.py`; no tool
  contract depends on it.
- **Dependency**: none on another ClickUp ticket, repo, or external service beyond DNSFilter's public
  API itself.
- **Dependency**: a real DNSFilter trial/test account, for the one manual end-to-end test case
  (TC-DNSF-012) — not available at design time; this does not block development, merge, or INT
  publish (SOP "no test account is not a blocker").

### Decisions made by DEV01

(Per mcp-track.md §2.4 — choices made without a human to ask, for this first version.)

- Consolidated DNSFilter's 229 endpoints down to 9 tools rather than mirroring endpoints 1:1 — kept
  only what the ticket's five nouns ("org", "network", "policy", "content categories",
  "traffic/threat reporting") require, folded the ~20 `traffic_reports/*` time-series/top-N endpoints
  into two parameterized tools (`metric`/`dimension` enums). Alternative: expose every
  `traffic_reports/*` endpoint as its own tool — rejected, would blow well past the SOP's practical
  tool-budget guidance and give an agent 20 near-identical reporting tools to choose between.
- Scoped to read-only for v1 (no `add_blacklist_domain`/`add_allowed_application`/etc. write
  endpoints wired up). Alternative: include the policy-mutation endpoints since DNSFilter exposes
  them — rejected because the ticket's own wording is "Review", not "manage" or "configure", and a
  write tool for a filtering policy is a customer-impacting action that deserves its own ticket with
  an explicit confirmation/guardrail design, not a default-on tool riding in on a read-only request.
- Left `query_logs` (raw per-query log rows) out of v1, covering "traffic/threat reporting" with the
  aggregate/top-N report tools instead. Alternative: add a `dnsfilter_get_query_logs` tool —
  deferred because DNSFilter's own docs steer this endpoint away from anything resembling the kind of
  broad export an agent conversation might casually trign; the top-N/summary tools answer the
  "what happened" questions the ticket actually asks for. Purely additive if wanted later.
- `secret_key` is stripped from every `Network` response rather than passed through — see
  Non-functional/Security. Not an alternative worth listing: returning a live vendor credential as
  tool output is a straightforward data-exposure bug, not a design trade-off.
- Picked `X-Dnsfilter-Api-Key` as the sole credential header (DNSFilter needs exactly one credential:
  its API key). Alternative: none — DNSFilter's auth is a single static key, so there is nothing else
  to parameterize.
